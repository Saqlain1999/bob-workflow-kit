# Choose a workflow and combine tools deliberately

Source review: **10 October 2026**. This comparison covers public documentation and source at the linked revisions. We did not install or run the external projects in this review. Their documented features, published results, and compatibility statements belong to those projects; they are not compatibility results for this kit.

Start with Bob's native features and the workflow your project already uses. Add this kit when its small instruction payload, explicit handoff notes, and evaluation guidance address a remaining problem. Planning, persistent context, checkpoints, and verification evidence already appear in other tools. This kit makes no claim to be the first, the only implementation, or a faster implementation of those ideas.

## Three different meanings of recovery

**Resume a conversation** when its saved task history is the right starting point. Bob's native history and resume facilities may be sufficient. A new IDE task has separate active context; the [context tutorial](https://bob.ibm.com/docs/ide/tutorials/context-window) explains how task history differs from a new task.

**Restore workspace files** when you intend to undo changes. Bob rollback, OnboardOps checkpoints, and Bob Control recovery have their own scope and restoration behavior. Review the affected files and intervening work before restoring. A kit checkpoint is not a backup or a rollback mechanism.

**Hand work to a fresh session** when you need a compact record of the goal, current state, decisions, checks, and next action. The kit's [recovery reference](../payload/skills/work-large-codebase/references/recovery.md) supports that process with ordinary files. The new session must read the checkpoint and inspect current source. The filename has no automatic loading semantics, and an old passing check can become stale without a new Git commit.

## Minimal coexistence steps

1. **Choose one primary workflow.** Use the project's existing plan, task list, and evidence location. A Spec Kit feature can keep its specification and tasks; a Debug Swarm investigation can keep its run artifacts. Add a short handoff that links those records only when a handoff is useful.
2. **Preserve applicable instructions.** Honor the user's task and project instructions. Keep the kit as a global default; do not overwrite `AGENTS.md` or project guidance to make another workflow fit. Bob documents that a same-name project skill overrides its global counterpart in both [IDE](https://bob.ibm.com/docs/ide/features/skills) and [Shell](https://bob.ibm.com/docs/shell/features/skills).
3. **Add only the capability needed now.** Inspect its current install instructions, names, paths, and prerequisites. Check for command or skill collisions. Do not install the whole table as a bundle or turn on unrelated MCP servers, hooks, and background services.
4. **Reuse context and evidence.** Link to the existing repository profile, specification, investigation record, and check logs. Record uncertainty and the source revision or inputs that support a claim. Refresh relevant facts after source, configuration, dependencies, or execution environment changes.
5. **Keep authorization explicit.** Retain the project's ordinary permission and review process. Installing a skill does not authorize every command in an example or approve a headless session. Review a runner's actual invocation and approval behavior before delegating work to it.
6. **Evaluate the actual combination.** Record the Bob client and version, OS and execution host, repository/fixture revision, active global and project instructions, enabled extensions, model or mode when exposed, permission configuration, and exact checks. Distinguish native resume from a fresh session reading a handoff. Record whether the client loaded the intended skill and report unavailable evidence as unavailable.

## What this kit can usefully contribute

The scope is modest: a reviewable installation of its own instructions, a concise task handoff format, and a way to collect evidence about a particular setup. Existing tools may already provide enough structure for your project. The [ecosystem guide](ecosystem.md) provides further learning and installation references, including offerings whose exact identity remains unresolved.

A useful interruption exercise changes a relevant source or configuration input after a passing checkpoint, preserves an unrelated teammate edit, and starts a fresh session with the goal and checkpoint path. Independent checks can establish whether the candidate implements the current requirement and preserves the protected edit. A separate observation is needed to establish whether the agent recognized that the old result was stale. Constructing that fixture or passing its helper tests does not establish Bob behavior.

Use the [evaluation guide](evaluation.md) and [companion evaluations](https://github.com/Saqlain1999/bob-workflow-evals) to record these outcomes against an explicit configuration. The same exercise can assess native Bob, an existing workflow, or a kit-assisted workflow. Publish failures, required interventions, and cases where added instructions provide no benefit. A small successful exercise supports a narrow result for that setup; it does not establish reliability across large repositories.
